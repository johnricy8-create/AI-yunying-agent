## 5. 数据质量策略

| 决策 | 说明 |

## 8. 阶段二决策（2026-10-26）

| 编号 | 决策 | 理由 |
|---|---|---|
| P1 | 对话模型使用智谱 `glm-4.7-flash` | 免费、200K 上下文、OpenAI 兼容；适合日报生成 |
| P2 | 关闭 thinking（`thinking.type=disabled`） | 保证 JSON 输出稳定、降低延迟；开启 thinking 时曾出现只返回推理 token、正文为空 |
| P3 | 向量模型使用智谱 `embedding-3`，1024 维 | 与 GLM 同一供应商、同一把 Key，减少密钥与依赖 |
| P4 | RAG 使用本地 NumPy 余弦索引 | 语料规模小，避免 Chroma/FAISS 的安装与维护成本 |
| P5 | 语料 = `knowledge/` 示例 SOP + `reports/history/` 历史日报 | 既有通用排查方法，也有历史案例；历史日报可重建 |
| P6 | 只把 Top-N 异常送模型，一次请求 | 控制 token 和免费模型 1 并发限制；失败可降级 |
| P7 | 1305/429/5xx/超时按 5s、15s 退避，最多 3 次 | 免费模型高峰期会过载；避免整份报告失败 |
| P8 | AI 结果按输入 + 检索块 + 模型 + 提示词版本缓存 | 同日重跑不重复消耗请求；缓存可强制刷新 |
| P9 | 阈值 v0.1 保持不变 | 用户确认；阶段三用真实数据再校准 |
| P10 | AI 失败时回退规则型建议，任务仍成功 | 报告可用性优先，不让模型故障阻断日报 |
| P11 | BGE-M3 不作为默认方案 | 避免第二个供应商与第二把 Key；阶段五再评估 |

| D3-5 | 阈值 v0.1 暂不自动调整 | 必须基于脱敏真实业务分布人工校准，不能凭模拟数据或猜测修改 |

| D3-8 | 移除 `refund_gt_sales` 错误规则 | 销售额是净额，退款金额可能大于净销售额；参考样本中曾误报 365 行 |
| D3-9 | 使用 UCI Online Retail 派生 300 商品 × 180 天、54,000 行参考样本 | 公开、规模足够、含退款/价格波动/缺失日期等真实特征；PV/UV/成本/库存明确标注为派生 |
| D3-10 | 参考样本不替代真实业务数据 | 英国礼品零售与数字商品差异大，只能用于工程验证；阈值仍需真实业务校准 |
| D3-11 | 增加阈值敏感度 OFAT + 2D 网格工具 | 观察单参数方向与组合影响；不自动改配置，不把参考结果当业务定案 |
| D3-12 | 提供的 Shopify 目录样本不用于每日销售日报/阈值校准 | 只有单日快照和价格事件，缺订单、销售额、PV/UV、退款、成本、库存数量；详见 `docs/data_assessment_shopify_catalog.md` |
| D3-13 | 先实现独立的商品目录/价格监控分支（路径 B） | 这份数据能立即支持价格/库存事件监控；与每日销售日报保持边界，不混用；销售日报等待订单/流量数据 |
| D3-14 | 用目录生成模拟销售面板，跑通完整日报演示 | 商品维度真实、销售/流量明确标注为模拟；只用于演示，不用于真实阈值校准 |
| D3-15 | 提供 `tools/run_demo.py` 一键演示，并在日报顶部写入数据来源横幅 | 降低首次使用门槛；防止把模拟销售误当真实数据 |

**参考样本发现**：

- 原 `refund > sales` 规则把 365 行合法的“退款大于净销售额”判成错误；已修正校验器与测试。
- 参考样本 54,000 行全部有效，0 隔离，521 行警告（成本高于当日售价、净销售额为 0）。
- 统计日 2011-11-27 为周日，300 商品触发 119 个异常，说明 v0.1 在该分布下偏敏感。
- 阈值敏感度测试（最后 30 天）：v0.1 日均异常 98.8 个、异常率 32.9%、高危日均 43.03；工程严格档约 36 个/天、12.0%。`pv_drop_ratio` 对异常数量影响最大；二维网格日均异常在 70.4–127.7 之间。
- 结论：参考样本只能说明“v0.1 偏敏感”，不能据此定业务阈值；保持 v0.1，等真实数据再用同一工具校准。

**待办**：参考样本已生成（`data/reference/`），已用于数据画像与规模验证；真实业务数据仍需你提供脱敏样例后再校准 v0.1。

## 10. 阶段四决策（定时执行）

| 编号 | 决策 | 理由 |
|---|---|---|
| D4-1 | 使用 APScheduler `BlockingScheduler` + CronTrigger | 文档要求；常驻进程内按 09:00 触发，结构简单 |
| D4-2 | 时区 `Asia/Shanghai` | 固定北京时间；Windows 依赖 tzdata |
| D4-3 | `max_instances=1` + 文件锁 `logs/scheduler.lock` | 同时防止调度器内部并发和手动运行并发 |
| D4-4 | 锁超过 6 小时自动清理 | 进程异常退出后不会永久阻塞 |
| D4-5 | 最多重试 2 次、间隔 300 秒，可配置 | 有限重试，避免无限等待 |
| D4-6 | 提供 `--run-now` 和 `--time HH:MM` | 不用等到第二天即可测试 |
| D4-7 | Windows 任务计划程序在登录/开机时启动 `scheduler.py` | 任务计划程序负责拉起常驻进程，APScheduler 负责每日触发 |
| D4-8 | 明确记录关机/休眠/进程退出不会执行 | 需要“唤醒计算机”和“错过任务后尽快启动”设置 |

**测试**：`tests/test_scheduler.py` 覆盖时间解析、文件锁、单次执行、报告生成、锁释放、调度器注册。当前共 72 个测试。
